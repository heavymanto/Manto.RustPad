# Changelog

Format inspired by "Keep a Changelog". No release has been made yet.

## [Unreleased]

### Changed
- **Dragging the scrollbar on a file with no line breaks no longer freezes the window**: a screen of rows cost up to 40 MiB of reads (every row looked for its line break up to the 1 MiB scan limit); on a 100 GB file of zeros one frame took ~120 ms and the window seemed stuck while the line index ran. The scan limit is now 128 KiB (a longer line is split into visual rows): ~17 ms per frame on the same file. Normal files are unaffected. `tests/grande_prova.rs` (ignored, `MRP_BIG=<file>`) times the drag on any big file.
- **The View menu is about the current work**: Theme and Language are only in Settings (F6 and F7 still work); the switches (jump bar, column mode, special characters, line numbers; in the Log menu follow and log colours) show a check mark when they are on.
- **Work in progress is easier to see in the status bar**: a progress bar next to the "indexing N%" / "searching N%" / "saving N%" text, and a tooltip on the indexing one that says line numbers appear when it is done and that you can keep working (7 languages).
- **Dialog windows: a close X always, bigger centred buttons** (G1; written by the junior, tests by ARCH): every dialog of the window (find, replace, go to, save, exit confirmation, jumps, menus, help) and the Settings window have their own title bar with an **X** at the top right, and the X is a Cancel (in the exit confirmation it keeps your work). The OK/Cancel/Find/Save buttons are at least 120 x 34 points, as wide as the longest label, centred in the window; the first one is the main action (filled blue), the others are neutral with a border. In the light theme the X is red (Windows-like), in the dark one grey with a red hover. The cross is drawn by hand (the font has no glyph for it).
- **Themes in the window: Automatic, Light, Dark**: `mrp-gui` offers only these (the four classic themes stay in the terminal editor). The default is **Automatic**: the window follows the system, light if the system is light, dark otherwise, and follows it live if it changes while the program is open. Choosing Light or Dark pins it; Automatic gives the system back. The theme is written in the settings file only when you chose it (before, changing any other setting pinned the current one). A `F6 menu in the window lists two rows. New tests: `tema_auto`, `finestrelle`.
- **Window: standard keys, jump bar position, movable dialogs**: in `mrp-gui` F3 = Find, F4 = Replace and F12 = read/edit (the terminal keeps F4 for editing; menus and tooltips show the window's keys); the page-jump bar now sits right under the toolbar, above the tabs; every dialog window can be dragged by its title and stays where it is left.
- **A "Log" menu in the window** (between View and Help): Filter lines, Follow the end of the file and Colour log lines, together (they were scattered in Edit and View).
- **Huge page jumps go straight to the line** (Phase 2, 1.1, the remainder): with the line index ready, a jump of 5000 rows or more (the `+1000` buttons, `Alt+PgDn` with a big multiplier) uses `offset_of_line` instead of walking the rows one by one: 280,000 rows now take milliseconds instead of 2.6 s (debug build) on the UI thread. The result is the one the walk gave (the cursor and the top of the view move by the same number of rows, stopping at the last page and the last row); without the index it still walks. 5 new tests.
- **`PieceTable` keeps its pieces in blocks** (at most 512 pieces each, with the byte total of each block) and an insert or delete rewrites only a small window around the change instead of copying the whole list; `len()` is O(1). Scattered edits: 1.8 ms → 0.9 µs per edit at 40,000 pieces, 2.6 µs at 400,000 ([docs/BENCHMARKS.md](docs/BENCHMARKS.md)). `PieceTable::pieces()` now returns a `Vec<Piece>` (a copy); `piece_count`, `piece`, `iter`, `with_chunk_capacity` and `Document::open_with_chunk` are new. 9 new tests with blocks of 4 pieces against a naive oracle. 
- **The line-number table is incremental** (`Document::line_count`, `offset_of_line`, `line_at_offset`): every block of the piece list has a label (`PieceTable::chunk_stamp`) that changes only when its pieces change, and the document remembers how many `\n` each label holds, so an edit makes it count again only the touched blocks instead of rebuilding a table over all the pieces. With a line count asked after every edit: 2.0 ms → 14 µs per edit at 40,000 pieces, 37 µs at 199,000. New: `PieceTable::chunk_count`, `chunk_pieces`, `chunk_len`, `chunk_stamp`, `Document::chunk_aggregations` (a diagnostic counter). 12 new tests ([docs/BENCHMARKS.md](docs/BENCHMARKS.md)).
- **README**: new screenshots of the window (six themes, light and dark) and a rewritten comparison of the two front ends (one engine, native controls in the window).

### Fixed
- **Found by the independent review of the code written without one (E26-E42, done by the junior and checked line by line):**
  - **Typing, Delete or Backspace at a cut inside a character** no longer corrupts the file: lines longer than the scan limit (128 KiB, 1 MiB before) are cut where the limit falls, even in the middle of a character, and Down or a click can put the cursor there; before an edit the cursor now goes to the start of the character (UTF-8, UTF-16/32, the East-Asian encodings).
  - **A tab being saved in the background kept its place in the session**: while the document was in the saving thread the session was rewritten without that tab, deleting its saved changes (a crash during a long save lost them).
  - **A replace in progress no longer hangs the editor** when the window closes a tab or opens a file at the same time (the run knew the tabs by position); both are refused while it runs.
  - **A file of yours named `untitled/untitled-N.txt`** in any folder is no longer taken for an untitled document when the session comes back (closing it would have deleted it); only the session's own `untitled` folder counts.
  - **Replace in all tabs says how many tabs were skipped** (an encoding that cannot take a regex).
- **Dragging in the window selected one row too far**: with the terminal chrome off (`mrp-gui`) a drag with the mouse ended on the row after the one under the pointer (the last row of text hid it in the old test). It now ends on the row under the pointer.
- **The strip under the text in the window** (the leftover space that does not fit a whole row) was always near-black; it now has the theme background (white in Light).

- **Replace, with glob / regex search and all tabs** (task E36), in the TUI and the GUI (Ctrl+H). The dialog has two fields (find, with; Tab switches), three modes (Alt+M: **text**, **glob** `* ? [abc] [!abc]`, **regex** with `$1`, `${name}`, `
`, `	` in the replacement), case (Alt+C) and scope (Alt+A: this tab or **all open tabs**). Enter first shows a **preview** (`3 matches in 2 tab(s)`, nothing is touched), a second Enter applies it; changing a field or an option drops the preview. All replacements of a document are **one undo step** (one Ctrl+Z puts everything back), the cursor follows the text, and an affected tab goes to edit mode. The same modes and case apply to Find (Ctrl+F, F3, Shift+F3, forward and backward, with the length of the match highlighted). How it works on big files: matching is **per line** (an occurrence never contains a newline, like `grep`), read in blocks of whole lines through the same snapshot the search uses, so nothing is loaded in memory and a regex cannot run away (the `regex` crate has no backtracking); the work runs in a thread, Esc stops it (on every tab), the keys are held meanwhile; the replacements are applied from the last to the first so positions do not shift, at most 2,000,000 in one go (more is refused with a message). Regex, glob and ignore-case need a UTF-8 document; plain exact text works in every encoding (a tab that cannot do it is skipped in the all-tabs scope and said so). A line longer than 16 MiB is read in pieces (an occurrence across a cut can be missed: documented limit). New dependency: `regex` (MIT or Apache-2.0). 56 new tests (30 core: glob translated exactly, 20 regex cases whose results come from Python `re.sub`, random texts against `str::replace` and a naive model with tiny blocks, one undo step; 26 TUI with the dialog, preview, tabs, encodings), 70 mutations killed or equivalent (the preview of a too-many case is tested with 2,000,001 lines).
- **Session: closing the editor does not lose your work** (task E35), in the TUI and the GUI. The tabs that were open, the cursor and mode of each, the encoding and, for tabs with unsaved changes, **the changes themselves** come back the next time. Unlike a copy of the text, only the edits are stored: the piece table is saved as the list of pieces (which part of the original file, which part of the added text) plus the added text, so a session over a 100 GB file with a few edits weighs a few kilobytes and the original file is never copied (`mrp_core::session`: a binary format with an FNV-1a check at the end; a truncated or altered file is recognised and skipped, a forged length cannot ask for memory). `Document::edit_state` / `restore_edits` rebuild the edits on a freshly opened document, and only if the file on disk is the one of that time (same length and same date to the nanosecond); the undo history is not saved. With a session on (the default when there is a profile folder, next to the settings: `session/`), F10 / Ctrl+Q / closing the window save the session and quit **without asking**; closing one tab by hand (Ctrl+W) still asks. The session also rewrites itself while you work (at most every 5 seconds, only when a document version, a cursor, a mode or the tab list changed), so a crash or a power cut loses at most a few seconds. `mrp` or `mrpg` with no file reopens the session; with files on the command line the tabs with unsaved changes of the last session still come back (nothing is lost), and a tab for the same file is replaced by the restored one. If a file changed on disk or vanished, its tab opens clean (or is dropped), a message says so and the saved record is kept in `session/stale/`. Two `mrp` running together do not write over each other: the first takes a file lock on the session folder (the system releases it if the process dies), the others work without a session. `--dump` and `MRPG_SCREENSHOT` never touch the session. 39 new tests (19 core with hand-built byte layouts, a model with random histories, corruption of every byte and every truncation; 20 for the tabs), 27 mutations all caught or equivalent (the cache clears and the undo check are redundant by construction, documented).
- **Tabs, in the TUI and the GUI** (task E34): several files open at once, each tab with its own `App` (its own line index, search, edit history and cursor), held by the new `Workspace` (`mrp-tui/src/workspace.rs`). Keys (with no dialog open): Ctrl+O asks for a path and opens it in a new tab (a file that is already open just comes forward; the TUI has a small path prompt for it, the GUI the native dialog), Ctrl+W closes the tab (with changes it asks first: save, discard, cancel), Ctrl+PgUp/PgDn and Alt+Left/Right switch tab, Alt+1..9 go to a tab, F10 / Ctrl+Q close everything asking tab by tab for those with changes. The theme and language chosen in one tab reach the others and the new ones. With more than one tab the TUI shows a bar on the first row (`name`, `name*` if modified; it scrolls to keep the active tab visible; a click selects a tab); the GUI draws its own strip with a close button per tab, middle-click closes, Ctrl+Tab / Ctrl+Shift+Tab cycle, and the File and View menus have Close tab, Next tab, Previous tab. Opening a file with unsaved changes no longer refuses: it opens a new tab (the old `gui.open_unsaved` message is gone). `mrp FILE...` and `mrpg FILE...` open one tab per file. Closing the window with changes in a background tab asks about that tab. 29 new tests (23 for the `Workspace`, 6 for the window), 21 mutations all caught after 7 new tests (language reaching new tabs, a tab that finishes saving while in the background, the click on the exact first column of a tab, a bar that fits exactly, the size of a tab brought forward, spaces around the path, ticks for background tabs).

Not done yet: installer and icon (mouse click and selection came with E32).
- **BOM and Windows-125x** (task E30): the cursor no longer writes in front of a BOM (`EF BB BF`, `FF FE`/`FE FF`, `FF FE 00 00`/`00 00 FE FF`; `Encoding::bom_len`): typing, Enter and paste at the start of the file go right after it, Backspace after the BOM does nothing and Delete in front of it removes the first character after it (before, any of them could break the file). The Windows-125x code pages now map their undefined bytes 0x80-0x9F (for instance 0x81, 0x8D, 0x8F, 0x90, 0x9D of windows-1252) to the C1 control with the same number, as Windows and the browsers do: before they were U+FFFD, which cannot be written, so a file with those bytes lost them on a save after an edit. 5 new tests, 7 mutations all caught.
- **Line-ending style** (task E29): `mrp_core::lineending::LineEnding` (`Lf`, `CrLf`, `Cr`) is detected at open from the first 64 KiB and decides two things. **Enter writes the style of the file** (`
` in a CRLF file, `` in a CR file, 16- and 32-bit units in UTF-16/32): before, Enter always wrote `
`, so editing a Windows file made it a mixed one. **Files with only ``** (classic Mac) are now split into lines: `Newline::Cr` is a new newline form (byte `0D`) for the one-byte and multi-byte encodings; the index, the row scan, the view and the column block follow it. The status line shows `CRLF` or `CR` after the encoding name (nothing for LF, so it is unchanged for most files). Rules: no `
` and at least one `` gives CR; more `
` than lone `
` gives CRLF; otherwise LF; a `` in the very last byte of the sample is not counted (it may be half of a cut `
`). A lone CR does not exist in UTF-16/32 (it counts as LF) and switching from a CR file to a 16/32-bit encoding turns the style into LF. Not done: converting a file from one style to another, a `--eol` option. 14 new tests with a model oracle for the index, 12 mutations all caught.
- **East-Asian multi-byte encodings** (tasks E27, E28): `shift-jis` (Windows-31J, aliases `sjis`, `cp932`), `euc-jp`, `gbk` (`cp936`, `gb2312`), `gb18030`, `big5` (`cp950`, `big5-hkscs`) and `euc-kr` (`cp949`, `uhc`), in the menu after the code pages, with `--encoding` and `--list-encodings`. The tables are those of the `encoding_rs` crate (WHATWG, new dependency, Apache-2.0/MIT); what is ours is everything an editor needs around them. A character is 1–4 bytes, the newline stays the byte `0A` (it never occurs inside a character), and an invalid or truncated sequence is one U+FFFD of one byte (the next byte is read again). **Going back is the hard part**: in Shift_JIS, GBK, Big5 and EUC-KR the second byte of a character can look like ASCII or like the first byte of another (the second byte of 表 is `5C`, a backslash), so the last bytes are not enough to know where the last character starts. `Encoding::last_char_len` / `char_start` restart from the nearest byte that cannot be a second byte (below 0x40 for Shift_JIS and Big5, below 0x30 for GBK/GB18030, below 0x41 for EUC-KR, any ASCII for EUC-JP) and walk forward; if there is none in the 1 KiB looked at (a line of pure ideographs), the first byte looked at is assumed to start a character, so the cursor can be one byte off on that line. Left, Backspace and the cursor snap when switching with `F9` use this. **Search** only accepts a match that starts at a character start (`Snapshot::with_boundary`), so searching for `\` no longer stops inside 表, and searching for `A` no longer stops inside ア (`83 41`). Typing a character the encoding cannot write is refused with the usual message; EUC-JP is read with its 3-byte JIS X 0212 form but `encoding_rs` does not write it. Never auto-detected (a Shift_JIS text still opens as windows-1252): choose it with `F9`. Not done: ISO-2022-JP and HZ (stateful), a Big5 sequence that decodes to two characters keeps only the first (four of them in Big5-HKSCS). **Checked against two independent sources**: `tools/gen_multibyte_oracle.ps1` (.NET, i.e. Windows) and Python's codecs agree on 100,000 sequences (every 1- and 2-byte sequence plus a sample of the 4-byte GB18030 ones) and `tests/multibyte.rs` compares them with `encoding_rs` row by row (mask and hash per lead byte, in 103 KiB); the entries where the sources disagree are left out (Windows maps some bytes to the private-use area, the Big5 variants differ, GB18030 `A3A0` is U+3000 for WHATWG and U+E5E5 for Windows and Python). 33 new tests: model oracle for backward steps, search at character starts for every start and chunk, a character across the 64 KiB read boundary, backward steps that need the whole line start. Checked: searching `A` in 128 MiB of Shift_JIS kanji rejects 326,903 candidates that fall inside a character in 0.3 s; 19 mutations: 13 caught at first, 4 survived (looking back only 4 bytes: they became tests) and 2 are equivalent (they only change how far back the walk starts).
- **UTF-32** (task E26): `utf-32le` and `utf-32be` join the encodings (`F9`, `--encoding utf-32le`, `--list-encodings`; now listed right after UTF-16, so the code pages moved from position 3 to 5 in the menu). It reuses the aligned-newline machinery of UTF-16: `Newline::Le32` (`0A 00 00 00`) and `Newline::Be32` (`00 00 00 0A`) have a 4-byte unit, and a newline only counts when aligned to 4 (U+A0000 followed by U+100000 contains `0A 00 00 00` shifted by 2 bytes and is not a newline). A character is exactly one 4-byte unit; a value above U+10FFFF or a surrogate (D800–DFFF) shows as one U+FFFD of 4 bytes, and a tail of 1–3 bytes that does not complete a unit is a single U+FFFD as long as the tail (the same as Python's `utf-32` decoder with `errors='replace'`, which is also the oracle for the tests). Detection at open: only the BOM, `FF FE 00 00` (LE) or `00 00 FE FF` (BE); UTF-32 without a BOM is not recognised (use `F9`). `FF FE 00 00` used to open as UTF-8 and is now UTF-32 LE, as Python does. Switching between any two encodings with a different newline form (UTF-8 ↔ UTF-16 ↔ UTF-32, LE ↔ BE) is refused while there are unsaved changes; the message now says "UTF-16/32" in the 7 languages (and fits in 40 columns). Typing, Enter, Tab, paste, column mode (the padding space is `20 00 00 00` / `00 00 00 20`) and copy (always UTF-8) all work on 4-byte units. 57 new tests with model oracles (index, document with edits, row scanning, search, view, TUI). Checked: a 256 MiB UTF-32 LE file with CRLF, accents, emoji and the shifted-newline trap characters has 1,594,082 lines and the index counts exactly that in 0.1 s (the wrong endianness gives 1 line, byte newlines give twice as many); 22 mutations: 20 caught at first, 1 survived (cursor rounding to 2 instead of 4: it became a test) and 1 does not compile (the compiler already guarantees it).
- **19 more single-byte code pages** (task E25): `us-ascii` (`ascii`; every byte above 0x7F is invalid, and only ASCII can be typed), `windows-874` (Thai, also `tis-620`), DOS `ibm775`, `ibm855`, `ibm857`, `ibm860`–`ibm863`, `ibm865`, `ibm869`, `ibm720`, `ibm1125`, and the Mac sets `mac-cyrillic`, `mac-centraleurope`, `mac-iceland`, `mac-turkish`, `mac-croatian`, `mac-romanian` (52 in all; the new ones come after the old ones, so nothing moves). Left out on purpose: `cp864` (its lower half is not ASCII), EBCDIC (its newline is not `0A`) and Mac Greek (Python and .NET disagree on two bytes and there is no third source). The tables are generated from Python codecs (`tools/gen_charsets.py`) and, new, **checked against a second source**: `tests/data/charsets_oracle_net.txt` is what .NET (Windows) decodes (`tools/gen_charsets_oracle.ps1`), and `tests/charsets_oracle.rs` compares all 47 tables byte by byte. Two kinds of difference are accepted: a byte the code page does not define, which .NET sends to a C1 control or a private-use character and we show as U+FFFD, and 26 listed cases where .NET keeps an older revision (ISO 8859-7:1987, ISO 8859-8, the Apple euro/Ohm/Romanian-comma updates, a KOI8-U variant, U+05BA in windows-1255), each with its reason; a listed case that stops being needed fails the test. 5 new tests.
- **UTF-16** (tasks E22, E23, E24): `utf-16le` and `utf-16be` join the encodings (`F9`, `--encoding utf-16le`, `--list-encodings`). In UTF-16 the newline is a 2-byte unit (`0A 00` or `00 0A`) that only counts when it is *aligned* to 2 bytes: the byte `0A` also appears inside other characters (U+010A, U+0A41) and two neighbouring units can form the pair shifted by one byte, so `mrp_core::newline::Newline` (`Byte`, `Le16`, `Be16`) finds it unit by unit. The line index, the document (`Document::set_newline`), row scanning, search (`Snapshot` ignores misaligned matches), the view, the column block (separator and padding spaces in the file's encoding) and the TUI all follow it; a character is one 2-byte unit or a surrogate pair (4 bytes), a lone surrogate or a stray last byte shows as U+FFFD. Detection at open: a BOM `FF FE` / `FE FF` (not `FF FE 00 00`, which is UTF-32), or, without a BOM, at least 8 bytes where one byte parity is mostly zero and the other almost never (ASCII-heavy text; CJK text without a BOM is not recognised: use `F9`). Switching to or from UTF-16 with `F9` is refused while there are unsaved changes (the edits would not be aligned): save first. Typing, Enter, Tab, paste and column paste write 16-bit units; copy gives UTF-8. Checked: a 1 GiB UTF-16 LE file (12,781,726 lines) opens in 0.37 s with 19 MiB of working set, the index counts every line (the wrong endianness gives 1 line, byte newlines give 2x), and the line is reachable after 5 s; a 200 MiB BE file counts 2,496,431 lines. 66 new tests (model-based for the index, scan and search); 31 of 43 mutations caught at first; of the 12 survivors 8 became tests and 4 are equivalent or unreachable (a defensive rounding, the fallback read path). Not done: UTF-32, East-Asian multi-byte encodings, converting between encodings, a cursor that skips the BOM.
- **Text encodings** (tasks E19 and E20): the document stays a sequence of bytes and an *encoding* says how they read as characters. UTF-8 (as before; an invalid byte is its own U+FFFD) and **33 single-byte code pages**: windows-1250..1258, ISO-8859-1..16, DOS 437/737/850/852/858/866, KOI8-R/U and Mac Roman (tables generated by `rust/tools/gen_charsets.py` from Python's codecs). Core: `mrp_core::encoding::Encoding` (`by_name`, `first_char`, `last_char_len`, `encode`, `encode_str`, `decode_lossy`, `detect`) and `ViewOptions::encoding`; all code pages are ASCII-compatible, so lines, the line index and search by bytes do not change. In `mrp`: the encoding is detected at open from the first 64 KiB (valid UTF-8 → UTF-8; otherwise windows-1252; a NUL byte → UTF-8), can be forced with `--encoding NAME` (`auto` is the default, `--list-encodings` lists the names) and changed any time with `F9` (a scrolling menu; the bytes are never touched). The status line shows the name when it is not UTF-8. Typing and pasting are encoded into the file's encoding, all or nothing (a character the code page lacks is refused with a message); copy gives UTF-8 text to the clipboard; search encodes the needle. `F9` is in the key bar (English `F5` label is now `Go`; other languages shortened to keep 80 columns) and in `F1`. 28 + 26 new tests; 25 of 29 mutations caught at first (the survivors became tests). Not done: UTF-16, East-Asian multi-byte encodings, converting a file from one encoding to another.
- **Portable mode**: with a `lang` folder next to `mrp.exe`, the languages *and* the saved settings (`settings.txt`) live there and nothing is written to the user profile (before, only the languages were portable). `rust/portable.ps1` builds such a folder (`mrp.exe` + `lang\*.json`). `F8` is now listed in the key bar; on 80 columns the bar uses single spaces so that every key, `F10` included, fits (Italian `F4` label shortened to `Modif.` for the same reason).
- **Column mode in `mrp`** (`F8`, shown as `COL` in the title): Shift+arrows/Home/End/PgUp/PgDn draw a rectangle of cells; typing, `Tab`, `Backspace`, `Delete` act on every row of the block at once (rows too short to reach the column are left alone), `Ctrl+C` / `Ctrl+X` copy and cut the block, `Ctrl+V` and terminal paste put a one-line text on every row or several lines one per row (refused, changing nothing, if the document has fewer rows). - **`rust/install.ps1`**: local install on Windows, same idea as Manto.FreeDisk's — copies `mrp.exe` to `%USERPROFILE%\.local\bin` and the seven language files to `%APPDATA%\mrp\lang`, replaces a running `mrp.exe` by renaming it, never touches `PATH` or the saved settings, and ends with a self-test (`--help`, `--dump` in English and in Italian from the installed language folder).

- **`PieceTable`** (`edit.rs`): the document as a list of pieces pointing into the original file (never copied) or a small
  buffer of additions; `insert`, `delete`, `read_range` with 64-bit offsets, canonical form (no empty pieces, contiguous
  pieces merged), errors that change nothing. Memory follows the edits, not the file size. 22 tests, with a naive

- **`Document`** (`document.rs`): a file plus its `PieceTable`, and **`save`**: writes a temporary file in the same folder,

  original untouched and no temporary file; if the file on disk changed since it was opened (length or date, or gone)
  the save is refused (`SourceChanged`) instead of overwriting someone else's work. 16 tests plus one 6 GB test.
- **`mrp-core` 0.1.0** — the engine, a library with no user interface yet:
  - `FileSource`: read-only memory-mapped file, 64-bit offsets, bytes (not
    UTF-8), empty file handled, error on anything that is not a regular file.
  - `LineIndex`: sparse line index (one checkpoint every 256 lines per 4 MiB
    block), built in parallel, with cancel and progress. The line separator is
    `\n`; a final line without `\n` counts as a line; the empty file has 0 lines.
    On a cold 6 GB file on a spinning disk a prefetch thread keeps the read
    sequential: 38 s (disk speed) instead of 145 s.
  - `find_next` / `find_prev`: byte search, block by block with overlap, with cancel.
  - `info` example: line count, checkpoints, timing and a few sample lines of any file.
